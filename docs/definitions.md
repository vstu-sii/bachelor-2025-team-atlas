# DoR/DoD критерии

## 1. Definition of Ready (DoR)

Критерии, по которым задача считается готовой к взятию в спринт:

- Definition of Ready для задач
- Задача считается Ready, если выполнены следующие условия:
- Есть чёткое описание задачи: цель, ожидаемый результат, ограничения.
- Определены входные данные — API, формат файлов, JSON-схема, макеты.
- Определён владелец задачи (ответственный разработчик).
- Определены зависимости (какие модули должны быть реализованы до неё).
- Понятны технические требования (алгоритмы, методы, используемые сервисы).
- Есть критерии приемки (Acceptance Criteria).
- Оценка трудозатрат понятна (story points).
- Нет блокировок — внешних или внутренних.
- Если задействуется LLM, должно быть готово:
  - промпт,
  - формат ответа,
  - fallback-поведение.
-UI-задачи: готов макет или прототип.

**Итог: задача может быть запланирована в спринт и разработчик имеет всё для выполнения.**

## 2. Definition of Done (DoD)

Критерии, по которым задача считается полностью завершённой:

- Definition of Done для функций
- Функция считается Done, если:
- Функциональность реализована полностью, без stub’ов.
- Все Acceptance Criteria выполнены.
- Код покрыт тестами:
  - unit-тесты ≥ 60%,
  - интеграционные тесты для API.
- Прошла ручное тестирование QA.
- Прошла code review минимум одним разработчиком.
- Документация обновлена:
  - описание эндпоинтов,
  - схема данных,
  - wiki.
- Функция задеплоена в dev/стейджинг и протестирована там.
- Нет ошибок P0/P1.
- Производительность соответствует требованиям (время генерации/парсинга/рендера).
- Логи и метрики собираются корректно (observability).
- LLM-модуль стабилен:
  - корректный ответ,
  - ограничение галлюцинаций,
  - fallback срабатывает при ошибке.
- UI отображается корректно на всех поддерживаемых разрешениях.

**Итог: Функция считается готовой к релизу.**

## 3. Метрики успеха продукта (Product Success Metrics)

### Продуктовые метрики
- Conversion to export — % пользователей, которые экспортируют презентацию после генерации.
- Completion rate — % пользователей, дошедших до конца процесса редактирования.
- Время до первого результата (TTFR) — от загрузки до готовой презентации.
- Удовлетворённость качеством (CSAT) — рейтинг пользователей после экспорта.
- Повторные использования — % пользователей, создающих ≥ 2 презентации.
- Bounce rate на шагах: загрузка → парсинг → улучшение → дизайн → экспорт.
- API LLM failure rate — частота ошибок ответов моделей.
- Average Slide Quality Score (экспертная оценка качества улучшений).

### Технические метрики
- Время обработки:
  - улучшение ≤ 30 сек,
  - генерация ≤ 45 сек.
- Uptime backend ≥ 99%.
- Ошибки парсинга ≤ 5%.
- Успешный экспорт ≥ 98%.

## 4. KPI для каждого спринта

Ниже — KPI на уровне команды, не отдельного сотрудника.

## Спринт 1 — Инфраструктура
- Наличие стабильного dev-окружения — 100% готовность
- Покрытие базовых модулей тестами ≥ 40%
- CI/CD pipeline настроен — 1 день отставания максимум

## Спринт 2 — Загрузка файлов
- Успешная загрузка файлов (PPTX/PDF) ≥ 95%
- Ошибки загрузки ≤ 2%
- Среднее время загрузки ≤ 2 сек

## Спринт 3 — Парсер
- Успешный парсинг текстов ≥ 90% случаев
- Время парсинга ≤ 5 сек
- Ошибки “parser failure” ≤ 5%

## Спринт 4 — LLM оптимизация
- Точность сохранения смыслов (экспертная оценка) ≥ 80%
- Ошибки LLM ≤ 3%
- Время ответа LLM ≤ 7 сек

## Спринт 5 — Генерация с нуля
- Генерация структуры презентации в 100% тестовых кейсов
- Логичность структуры (оценка человека) ≥ 80%
- Время генерации ≤ 12 сек

## Спринт 6 — Применение дизайна
- Применение шаблона без критических ошибок: 95%
- Среднее время рендеринга ≤ 3 сек
- Визуальная согласованность ≥ 80% (оценка UX)

## Спринт 7 — Предпросмотр и редактор
- Задержка интерфейса ≤ 200 мс
- Безошибочное автосохранение ≥ 98%
- Crash rate UI ≤ 1%

## Спринт 8 — Экспорт
- Успешный экспорт PPTX/PDF ≥ 98%
- Время экспорта ≤ 5 сек
- Ошибки структуры (сломанные слайды) ≤ 3%
